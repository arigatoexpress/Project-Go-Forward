# Incident: Schema-Text Body on /healthz/ and /api/admin/verify

**Date:** 2026-05-01  
**Severity:** Medium (intermittent, not reproducible at will)  
**Status:** Mitigated (see PR `fix/schema-text-body-cause`)

|---|-----------|----------|--------|----------|
| 1 | ~12:08 | `/healthz/` | GET | not captured |
| 2 | ~19:30 | `/api/admin/verify` | POST | not captured |

Both sightings were single-shot — the next request to the same endpoint returned a correct body. Could not reproduce with 30 parallel requests on 2026-05-01 20:00 UTC.

## Bad Body Shape

The response was **not valid JSON**: keys were unquoted, values were type-name strings.

### Sighting 1 — `/healthz/`

```
{
  dependencies:
  {
    db: string,
    drive: string,
    email: string,
    secrets: string
  }
  sha: string,
  status: string,
  uptime_s: int,
  version: string,
  warnings:
  [
    string
  ]
}
```

### Sighting 2 — `/api/admin/verify`

```
{
  success: bool,
  token: string
}
```

---

## Distinguishing Characteristics

1. **Not valid JSON** — keys unquoted, value literals like `string`, `int`, `bool`.
2. **Keys are alphabetically sorted** — `dependencies`, `sha`, `status`, `uptime_s`, `version`, `warnings`. The real `healthz()` dict has insertion order: `status`, `version`, `sha`, `uptime_s`, `dependencies`, `warnings`. Alphabetical sorting is a strong indicator this did NOT come from the Python runtime dict serialization.
3. **Values are type names** — `string` (JSON Schema / TypeScript style), `int` and `bool` (Python style). This inconsistency does not match any single schema format exactly.
4. **Body starts with `{` + newline** — normal FastAPI `JSONResponse` always starts with `{"` (brace + quote) because `json.dumps` writes the first key immediately. The schema-text body starts with `{\n  key:` (brace + newline + indent + unquoted key).
5. **Structure exactly mirrors real response shape** — the bad body has the same keys as the real response, just with type names as values.

## Root Cause Hypothesis

### Primary: CDN / GFE Schema-Cache Leakage (Most Likely)

The production service at `sapphirealpha.xyz` sits behind **Google Frontend (GFE)** (confirmed via `server: Google Frontend` response header). FastAPI's auto-docs were enabled in production:

- `GET /openapi.json` → 200 (OpenAPI schema in JSON format)
- `GET /docs` → 200 (Swagger UI HTML + CDN JS)
- `GET /redoc` → 200 (ReDoc HTML)

The OpenAPI schema for `/healthz/` includes a response description with properties rendered as type descriptions. A CDN or edge caching layer may have:

1. Served a schema-text document (possibly cached `/openapi.json` content rendered in a non-standard format, or an inline schema description generated by the Swagger UI layer) in response to a real API request, due to a cache key collision, stale entry, or edge-worker bug.
2. The alphabetical ordering matches how JSON Schema properties are typically listed.

**This is the most parsimonious explanation** because it accounts for:
- Alphabetical key ordering (cache/schema layers sort keys; Python dicts do not)
- One-shot nature (brief cache window)
- Both affected endpoints being "simple" endpoints whose schema could be cached as static content

### Secondary: Plain Dict Return on `/api/admin/verify`

The success path of `verify_admin_pin` returned a plain Python dict:

```python
return {"success": True, "token": token}   # line 2395 (before fix)
```

All other return paths in the same function used `JSONResponse(...)` explicitly. In FastAPI, returning a plain dict causes the framework to apply `jsonable_encoder` and then serialize via the default response class. Under normal operation this produces identical output to `JSONResponse(...)`. However, under specific edge cases (response model validation, middleware interaction, serializer version mismatch) the behavior could differ.

### Ruled Out

- **BaseHTTPMiddleware body corruption** — 4 stacked `BaseHTTPMiddleware` instances are known to cause issues but would produce empty/garbled bodies, not schema-text bodies.
- **FastAPI version bug** (`0.123.10`) — no known issues matching this pattern at time of investigation.
- **GFE intercepting `/healthz/`** — GFE reserves the exact path `/healthz` (no slash), not `/healthz/`. The bad sighting was on `/healthz/` which FastAPI handles.

## Mitigations Applied (PR `fix/schema-text-body-cause`)

### 1. Disable OpenAPI docs in production

```python
_is_cloud_run = bool(os.environ.get("K_SERVICE"))
app = FastAPI(
    docs_url=None if _is_cloud_run else "/docs",
    redoc_url=None if _is_cloud_run else "/redoc",
    openapi_url=None if _is_cloud_run else "/openapi.json",
)
```

**Rationale:** Eliminates the CDN schema-cache leakage vector entirely. If `/openapi.json` is not accessible in production, no intermediary can serve its content in place of a real response.

### 2. Explicit `JSONResponse` on all `/api/admin/verify` return paths

```python
return JSONResponse({"success": True, "token": token})
```

**Rationale:** Removes the only plain-dict return in the function. All paths now explicitly construct the response, leaving no room for FastAPI's implicit serialization to behave differently.

### 3. `_BodyShapeGuard` pure ASGI middleware

A pure ASGI middleware (NOT a `BaseHTTPMiddleware` — avoids async buffering issues) that peeks at the first body chunk of JSON responses on watched paths. Logs `ERROR` with `SCHEMA_TEXT_BODY_BUG` key if body starts with `{` + non-`"`.

**Rationale:** The next occurrence will be captured in Cloud Logging immediately, with the path and first 60 bytes of the bad body. To retrieve the log:

```
gcloud logging read \
  'resource.type="cloud_run_revision" AND resource.labels.service_name="project-go-forward" AND textPayload:"SCHEMA_TEXT_BODY_BUG"' \
  --project=tho-ai-agent --format=json --limit=10
```

### 4. Regression tests

- `test_admin_verify_body_is_strict_json_with_concrete_values` — verifies `/api/admin/verify` never returns a schema-style body.
- `test_openapi_docs_disabled_in_cloud_run` — verifies `/openapi.json`, `/docs`, `/redoc` do not serve JSON in Cloud Run mode.
- Existing: `test_healthz_body_is_strict_json_with_concrete_values` (already in place from PR #51).

1. **Capture the trace ID** — `curl -D /tmp/headers.txt https://sapphirealpha.xyz/healthz/` and look for `x-cloud-trace-context`.
2. **Check Cloud Logging** with the trace ID (see command above).
3. **Check Cloudflare/GFE cache** — if a CDN is in front of the GFE, check its cache headers and purge policy for `/healthz/` and `/api/admin/verify`.
4. **Check Cloud Run revision** — if multiple revisions are deployed, one may have different behavior.
5. **Check the `_BodyShapeGuard` log** — after this PR is deployed, any future occurrence will log `SCHEMA_TEXT_BODY_BUG` with path + first 60 bytes, which should reveal whether the bad body comes from the Python app or an upstream layer.
